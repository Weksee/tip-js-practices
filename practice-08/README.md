## 1. Цель работы и результат
Цель — организовать взаимодействие компонентного интерфейса с HTTP API: загрузку при изменении зависимостей, очистку эффекта, операции изменения и повторное получение актуальных данных.

В ходе работы реализован хук `useTaskData`, который связывает React-компоненты с сервером, обрабатывает состояния загрузки, ошибки и отменяет устаревшие запросы.

## 3. Обязанности модулей
- `App.jsx` — хранит фильтры и состояние редактирования, связывает хук с компонентами.
- `hooks/useTaskData.js` — выполняет GET-запросы, управляет мутациями, отменяет устаревшие запросы через `AbortController`.
- `api-client.js` и `task-api.js` — HTTP-клиент и предметный API (перенесены из ПР6).
- `TaskForm.jsx`, `TaskList.jsx` — отображение и асинхронная форма.

## 4. Состав зависимостей и cleanup
Эффект загрузки зависит от `api`, полей фильтров (`q`, `completed`, `priority`, `categoryId`) и счётчика `revision`. В `cleanup` отменяется запрос через `AbortController` и сбрасывается флаг актуальности, чтобы запоздавший ответ не изменил состояние.

## 5. Защита от устаревших ответов и повторных мутаций
- Для чтения: при смене фильтра старый запрос отменяется, а его результат игнорируется благодаря проверке `active`.
- Для мутаций: используется `useRef` для блокировки повторного вызова до завершения текущего. Если компонент размонтирован, мутация отменяется через `AbortController`, но серверная операция при этом не откатывается.

## 6. Различие ошибок изменения и обновления
`mutationError` (ошибка POST/PATCH/DELETE) хранится отдельно от `error` (ошибка GET). Если сохранение прошло успешно, но последующий GET завершился ошибкой, показывается ошибка обновления, а данные не теряются.

## 7. Индивидуальный вариант (Вариант 3)
- **Начальный фильтр:** `priority=high`.
- **Сценарий:** изменить приоритет задачи на «Средний».
- **Запросы:** PATCH `/api/tasks/:id` (тело: `{ priority: "medium" }`) → GET `/api/tasks?priority=high`.
- **Результат:** задача исчезает из выборки после ответа сервера (так как фильтр остался `high`), общая статистика обновляется.

## 10. Ответы на контрольные вопросы
1. **Зачем нужен эффект?** Чтобы синхронизировать компонент с внешней системой (сервером) после рендера, не блокируя его.
2. **Когда вызывается cleanup?** Перед повторным запуском эффекта при изменении зависимостей и при размонтировании.
3. **Почему callback не async?** `useEffect` ожидает функцию очистки, а `async`-функция возвращает Promise, что нарушает контракт.
4. **Почему snapshot нет в зависимостях?** snapshot — результат загрузки, а не её причина. Его изменение не должно вызывать новый запрос.
5. **Почему важна стабильная ссылка на api?** Если `api` создаётся заново при каждом рендере, эффект будет запускаться бесконечно.
6. **Зачем проверять актуальность, если есть AbortController?** Отмена может не сработать (например, кэш или тестовая заглушка), поэтому нужна дополнительная проверка.
7. **Почему защита нужна в catch?** Чтобы запоздавшая ошибка отменённого запроса не перезаписала актуальное состояние.
8. **Что проверяет StrictMode?** Корректность очистки эффектов (setup → cleanup → setup).
9. **Почему state pending недостаточно?** Два синхронных вызова могут увидеть старое значение `pending` до его обновления. Нужен `useRef`.
10. **Что означает true от saveTask?** Успешное выполнение мутации. Ошибка последующего GET — это отдельная ошибка обновления.
11. **Почему нельзя автоматически повторять POST?** Это может создать дубликат записи на сервере.
12. **Почему смена фильтров не отменяет мутацию?** Мутация — это пользовательское действие, оно должно завершиться на сервере.
13. **Что происходит с серверной операцией после отмены?** Сервер может её завершить, клиент просто не узнает результат.
14. **Чем meta.total отличается от общего числа?** meta.total — количество записей после фильтрации на сервере.
15. **Что не проверяет jsdom?** CORS, реальный рендеринг, визуальные состояния, клавиатурную навигацию.
