## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | Сначала синхронный код, затем микрозадачи (Promise), затем таймер. |
| Фактический результат | A: синхронный код; B: начало async-функции; C: конец синхронного кода; D: обработчик Promise; E: продолжение после await; F: задача таймера | Синхронный код (A, B, C) выполняется сразу. Микрозадачи (D, E) идут следующими. Таймер (F) — макрозадача, выполняется последней. |

Таймер с задержкой `0` не выполняется немедленно, так как его коллбэк ставится в очередь макрозадач, которые обрабатываются только после того, как стек вызовов опустеет и выполнятся все микрозадачи.

## Наблюдение за HTTP-ответом

| Свойство | Фактическое значение | Что означает |
|---|---|---|
| URL запроса | `http://127.0.0.1:5505/api/tasks` | Адрес для получения списка задач |
| Метод | GET | Запрос на чтение данных |
| Статус | 200 | Успешный запрос |
| `response.ok` | true | Статус находится в диапазоне 200-299 |
| `Content-Type` | `application/json; charset=utf-8` | Тело ответа содержит JSON |
| id полученных задач | `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]` | 12 задач из общего набора |
| `meta.filters` | `{}` | Фильтры не применялись |

Запрос `/health` возвращает статус `ok`. Запрос `/tasks/25` возвращает задачу. Запрос `/tasks/999` возвращает 404 с JSON-ошибкой `TASK_NOT_FOUND`.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP-сервер с задачами и категориями |
| `src/api-client.js` | Базовый HTTP-клиент (fetch, тайм-аут, обработка статусов и JSON) |
| `src/task-api.js` | Предметный модуль (маршруты задач и категорий, проверка схем) |
| `src/variant.js` | Данные индивидуального варианта (фильтры) |
| `src/main.js` | Контрольный сценарий в терминале |

`fetchFn` передаётся в `createApiClient` для того, чтобы можно было подменить сетевой запрос в тестах (модульные проверки без реальной сети). HTTP-ошибки проверяются отдельно от сетевых, потому что `fetch` не отклоняет Promise при статусах 4xx и 5xx, это просто ответ сервера. JSON проверяется по контракту, потому что синтаксически корректный ответ может не содержать нужных полей или иметь неверный тип данных.

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач (id от 1 до 34) |
| `getTasks({ completed: false, priority: "high" })` | id `[4, 13, 34]` |
| `getTaskById(25)` | Объект задачи с id=25 |
| `getCategories()` | id `[1, 2, 3]` |
| `loadInitialData(...)` | Задачи, категории и meta |

Задачи проверяются на положительный id, строку title (до 100 символов), boolean completed, допустимый priority и положительный categoryId. Категории проверяются на id и name. Уникальность id проверяется через `Set`. `meta.total` должен совпадать с длиной массива.

## Последовательная и параллельная загрузка

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 300 | 300 | 300 | Задержки складываются (150 + 150) |
| `Promise.all` | 150 | 150 | 150 | Запросы идут параллельно |

*Promise.all* запускает оба запроса одновременно, поэтому общее время равно времени самого долгого запроса, а не их сумме.

## Вывод

В ходе работы освоены асинхронные операции в JavaScript (Promise, async/await), работа с HTTP-запросами через `fetch` и проверка ответов. Реализован клиент, который различает HTTP-ошибки (например, 404), сетевые ошибки (сервер недоступен), неверный формат ответа (не JSON или неверная схема), тайм-аут и явную отмену запроса. Изучено, что `Promise.all` не отменяет остальные запросы при ошибке одного из них, а `fetch` не отклоняет Promise при статусах 4xx и 5xx. Исправлены ошибки, связанные с валидацией входных данных (дробный `timeoutMs`, неверные фильтры).
